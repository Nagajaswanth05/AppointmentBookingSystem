# Assumptions, Invariant, Limitations

## Booking invariant
For a given provider, no two **active** appointments overlap. Intervals are half-open
`[start, end)`. Back-to-back appointments (`end == next start`) are allowed. Cancelled
appointments never block. Different providers are independent.

## Assumptions
1. No starter project was supplied; this implementation uses an in-memory store.
2. **UTC only.** Timestamps are ISO-8601 ending in `Z`. Offsets and zone-less values are rejected, not converted.
3. A booking is `providerId + clientId + start + end` (end must be after start). `clientId` is required but never affects conflicts.
4. Identifiers are opaque, non-blank strings, compared **exactly** (case-sensitive, no trimming). `dr-a` and `DR-A` are different providers.
5. Appointment ids are generated by the service (UUID); callers cancel by that id.
6. "Overlap" means sharing any positive-length span of time; touching endpoints do not.
7. Cancelling is permanent (no un-cancel); cancelled records are retained.
8. Bookings in the past, and arbitrarily long or short appointments (≥ 1 ns, since `Instant` has nanosecond precision), are allowed. No business-hours or max-duration rules.
9. The service runs as a single process; all writes go through `BookingService`.
10. The application exposes a Spring Boot REST API and has no authentication. This is an assessment prototype, not production-ready software.

## Limitations & follow-up risks (within scope)
- **Lock scope is one `BookingService` instance.** Its per-provider locks coordinate calls through that instance only; separate service instances do not share locks, even in the same JVM, and separate application processes are not coordinated. All writes must go through the same service instance for the invariant to hold. With a real database, use a transaction/row lock or an exclusion constraint (see design spec §6).
- **Provider locks are never evicted.** `providerLocks` retains one monitor for every provider ID seen for the lifetime of the service instance, so memory use grows with the number of distinct providers.
- **No persistence.** All data is lost on restart.
- **O(n) conflict scan per booking** over a provider's appointments (including cancelled ones). Fine for a prototype; add an index/interval structure or DB index for scale.
- **Unbounded appointment growth.** Cancelled appointment records are retained and never evicted.
- **No idempotency key.** A client that retries a timed-out `book` could create a second, conflicting-or-not, appointment. A client-supplied request id would fix this.
- **Cancel authorisation is out of scope**: anyone with an id can cancel it.
- **Strict timestamp parsing** rejects valid ISO offsets such as `+00:00`; this is a deliberate simplification and could surprise API clients.
- **Concurrency tests are probabilistic.** They failed reliably against a deliberately broken (lock-removed) version, but a pass is evidence, not a proof. Review the locking by reasoning as well (design spec §5).
- **No clock/time-of-day rules** (past bookings, working hours, buffers between appointments).
- **No authentication or rate limiting** on the REST API.
- **No idempotency on `POST /api/appointments`.** A client retry after a timeout can create a second appointment (or get a 409 against its own first attempt).
